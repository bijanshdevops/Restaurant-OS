## [Unreleased]

### Added
- Precise Recipe/BOM (Phase 13): three sub-features shipped together, all ADMIN-only (matching the existing recipe/BOM access model) — (1) **Yield % (waste)**: `RecipeItem`/`SubRecipeItem` gained a `yieldPercent` field (default 100); the effective inventory deduction for a line is `quantity / (yieldPercent / 100)`, so a 50% yield on a 2-unit line deducts 4 units. (2) **Sub-recipes**: a new `SubRecipe`/`SubRecipeItem` model pair supports arbitrarily nested sub-recipe-of-sub-recipe formulas, with cycle detection (`assertNoSubRecipeCycle`, BFS-based) and a depth cap (`MAX_SUBRECIPE_DEPTH = 12`) enforced during expansion; a sub-recipe in use by a menu item or another sub-recipe cannot be deleted. (3) **Modifiers/add-ons**: new `ModifierGroup`/`Modifier`/`MenuItemModifierGroup`/`ModifierRecipeItem` models let a menu item offer optional add-ons with a `priceDelta` and a signed inventory effect (a modifier's recipe-line quantity can be negative, e.g. "no cheese"; the deduction is clamped at zero, never negative); each `ModifierGroup` enforces `minSelect`/`maxSelect` server-side at order time. All formula expansion (base recipe + sub-recipes + selected modifiers) runs through one shared library, `src/lib/recipeExpansion.ts`, used by both real order-time stock deduction and the cost-analysis (Phase-just-prior) screen, so there is never a second, divergent implementation of "what does this item's formula mean" — cost analysis deliberately still excludes modifier effects in this pass. As part of this phase, a pre-existing latent bug was found and fixed: refund restocking previously recomputed quantities from the *live* recipe, so editing a recipe between an order and its later refund would silently restock the wrong amount. Fixed by snapshotting the fully-expanded per-unit ingredient usage (`OrderItemIngredientUsage`) and the selected modifiers (`OrderItemModifier`) once, at order-creation time, and having both the stock-deduction step (immediate for POS, deferred to payment-finalization for online orders — timing unchanged from before this phase) and the refund restock step (`refund.ts`) read that snapshot instead of the recipe as it exists today. Separately, an unplanned reliability bug in `recipeExpansion.ts` itself was found and fixed during this phase's own test development: calling the shared client from inside a `prisma.$transaction` callback (instead of the transaction's own client) could intermittently starve the connection pool, causing rare non-deterministic order/sub-recipe-save failures with no surfaced error; fixed by threading an explicit database-client parameter through every function in the library and having every transactional caller (`order.ts`, `subRecipe.ts`) pass its own transaction client.
- `tests/preciseRecipe.test.ts` covering ADMIN-only access control on all 8 new actions, yield-% deduction math, sub-recipe expansion and cost roll-up, direct and indirect sub-recipe cycle rejection, delete-while-in-use rejection, modifier price/inventory effects (including the zero-floor clamp on a negative modifier), `minSelect`/`maxSelect` enforcement, a modifier rejected when it belongs to a different menu item, and — the key correctness test — that refunding an order restocks the *original, snapshotted* ingredient amount even after the underlying recipe was changed multiple times between order creation and refund, for both the POS and online-order (payment-finalization) paths.
- Waitlist & reservation deposits (Phase 12): a new `WaitlistEntry` table (`WAITING`/`SEATED`/`CANCELLED`) for walk-in guests with no future time or pre-assigned table — deliberately kept separate from `Reservation` for that reason — with `getWaitlist`, `joinWaitlist`, `seatFromWaitlist`, `cancelWaitlistEntry` (`ADMIN` + `CASHIER`, matching the existing reservation access model). `seatFromWaitlist` mirrors `updateReservationStatus`'s `SEATED`-branch table-sync logic (table becomes `OCCUPIED`) inside a `$transaction`. Separately, `Reservation` gained `depositAmount`/`depositRefundedAt`: an optional staff-collected deposit at `createReservation` time books a real `INCOME` transaction (new system category `INCOME_RESERVATION_DEPOSIT`, `referenceType: 'RESERVATION_DEPOSIT'`) in the same `$transaction` as the reservation. Refunding a deposit is a new, separate, explicit action (`refundReservationDeposit`) — never triggered automatically by any reservation-status change — that books a full, unconditional refund (an `EXPENSE` transaction, `EXPENSE_RESERVATION_DEPOSIT_REFUND` category) at any time, including after cancellation or no-show, per the confirmed "full refund at any time" policy; the original `INCOME` transaction is never touched, consistent with the Phase 7/10 reference-backed-transaction rule. Deposit/refund events are not added to the Phase 11 audit log (out of that phase's locked-in scope). Reservations UI (`/dashboard/reservations`) gained an optional deposit-amount field on reservation creation, a refund action per reservation, and a new waitlist panel (join/seat/cancel).
- `tests/waitlistDeposits.test.ts` covering access control (`CASHIER` allowed, `CHEF` denied, on every new action), deposit collection producing a correctly-shaped `INCOME` transaction (and no transaction at all when no deposit is given), deposit refund producing a correctly-shaped `EXPENSE` transaction while leaving the original `INCOME` transaction untouched, blocking a second refund and blocking a refund with no deposit, refunding successfully regardless of reservation status (including after `CANCELLED`), the waitlist join→seat flow's table-status sync, seating-twice rejection, waitlist cancel, and branch isolation for both the waitlist and deposit-refund actions.
- Audit log (Phase 11): a new `ADMIN`-only activity log (`getAuditLogs`, `getAuditActionList`, `/dashboard/audit-log`) recording sensitive events only — user login (success and failure), user creation/deletion, financial-transaction deletion/recategorization, refund creation, restaurant/Modian settings updates, and payroll runs. Backed by a new `AuditLog` table (`actorUserId` nullable with `onDelete: SetNull` so deleting a user never blocks on its own audit history, `actorName`/`actorRole`, `action` enum, `entityType`/`entityId`, `metadata` JSON, `success`, `createdAt`) and a single non-throwing `logAudit()` helper (`src/lib/auditLog.ts`) that accepts the current `prisma.$transaction` client so log rows for `runPayroll`/`createRefund` commit or roll back atomically with the operation they describe. Role changes are explicitly *not* logged, because no role-update action exists anywhere in this codebase (roles are only ever set once, at user creation) — confirmed by re-reading `user.ts` before finalizing this phase's event list. Every normal read, and every ordinary POS/online order, is deliberately never logged, per the "sensitive events only" scope decision.
- `tests/auditLog.test.ts` covering ADMIN-only access to the log viewer, a correctly-shaped log row for every instrumented event (login success/failure including the no-actor/no-password case, user create/delete, transaction delete/update, refund creation, both settings-update paths with the Modian API key never appearing in logged metadata, and payroll runs), and that an ordinary POS order produces no audit row at all.
- Refunds & returns (Phase 10): a new ADMIN-only module (`getRefunds`, `findOrderForRefund`, `createRefund`, `/dashboard/refunds`) for reversing a `COMPLETED` order, either partially (specific item/quantity lines) or fully (the entire remaining, unrefunded balance). Refund state is tracked entirely through two new tables (`Refund`, `RefundItem`) and a new `OrderItem.refundedQuantity` counter — deliberately not a new `Order` status, so `Order.status` stays `COMPLETED` forever and nothing in the existing kitchen/active-orders status filtering had to change; only `COMPLETED` orders are eligible (an order still mid-kitchen must be advanced or cancelled first, out of scope for this phase). Each refund event books a brand-new `EXPENSE` transaction (system category "مرجوعی و استرداد") rather than touching the order's original `INCOME` transaction, consistent with the Phase 7 rule that a reference-backed transaction can never be deleted or reduced — `getFinancialSummary`/`getProfitAndLossReport`/VAT netting all pick this up automatically with no code changes. Refunded item quantities always restock `BranchInventoryStock` via the menu item's recipe (BOM), on the assumption the returned goods are sellable — there is no damaged/spoiled-goods distinction. Tax is reversed proportionally to the refunded items' share of the order's original subtotal; packaging cost is only refunded on a full refund (using the *current* restaurant-settings packaging cost, since `Order` never persisted the packaging cost actually charged at checkout time) and never prorated for a partial refund; delivery fee is never refunded in any case. When the order has a customer, loyalty points and lifetime stats are reversed proportionally to the same ratio (points clawed back for points earned, points returned for points redeemed on that order, `totalSpent` decremented and floored at zero, tier recomputed), and `totalOrders` is decremented only when the refund is explicitly a full refund. As part of this phase, a pre-existing gap was fixed in `createOrder`: `Order.pointsEarned` was never persisted for POS orders (only the online-order flow set it), which would have silently zeroed out the new proportional points-clawback for the majority of orders — it is now stored at order-creation time using the same calculation `awardLoyaltyForOrder` already performed. Sales analytics (Phase 9) is *not* updated to reflect refunds in this phase — refunded revenue continues to appear at its original, unadjusted value there.
- `tests/refund.test.ts` covering ADMIN-only access control, `COMPLETED`-only eligibility, full-refund total/eligibility-exhaustion (including that a fully refunded order can't be refunded again), the automatic EXPENSE transaction and its non-interference with the original INCOME transaction, proportional tax math on partial refunds, over-refund and invalid-line-item rejection, inventory restock correctness across a partial-then-full refund sequence, and proportional loyalty/customer-stat reversal (including the `totalOrders` full-refund-only decrement and the `Order.pointsEarned` persistence fix).
- Sales analytics / BI dashboard (Phase 9): a new read-only reporting module (`getSalesAnalytics`, `/dashboard/analytics`) built purely from existing order data — no new data-entry surfaces. "Real sales" are defined as any order whose status is not `CANCELLED`/`AWAITING_PAYMENT` (matching exactly when the accounting module books income), a fixed rule that is not user-configurable; date range and branch remain the only filters, defaulting to the last 30 days when no range is given. Reports include KPI cards (total revenue/orders/average order value), a daily revenue trend, top-10/bottom-10 menu items by revenue/quantity (limited to items with at least one sale in the period), a per-branch comparison, a 24-hour peak-hours breakdown, and a sales-channel (dine-in/takeaway/online) mix. Access is ADMIN + ACCOUNTANT, reusing the Phase 5/7 branch-scoping pattern (ACCOUNTANT locked to their own branch; branch-less online orders remain visible under any branch filter, as in accounting). No export feature and no forecasting/cohort analytics in this pass.
- `tests/analytics.test.ts` covering access control (ADMIN/ACCOUNTANT allowed, CASHIER/CHEF denied), the default 30-day window, the CANCELLED-exclusion rule for "real sales," explicit date-range filtering, per-item/per-branch/per-hour/per-channel aggregation correctness, and ACCOUNTANT branch-scoping (including that a non-admin's own-branch view still surfaces branch-less online orders, and that a non-admin cannot override their branch via a client-supplied `branchId`).
- Kitchen display multi-station routing (Phase 8): a new optional `MenuItem.kitchenStation` free-text tag (set by ADMIN in menu management), and station tabs on the existing kitchen board (`/dashboard/kitchen`) computed live from what's currently active in the queue — selecting a station filters tickets to the ones containing that station's items and shows only those items within each ticket. The pre-existing single-queue PENDING/PREPARING/READY board, its elapsed-time-since-order warning, and its ADMIN+CHEF page access (with `getActiveOrders`/`updateOrderStatus` staying CASHIER-accessible as before) are all unchanged. Order status remains per-order rather than per-item, so a ticket's status buttons still advance the whole order even from a single-station view; there is no configurable prep-time target/SLA, only the existing simple elapsed-time warning.
- `tests/kitchen.test.ts` covering kitchen-station CRUD on menu items (including ADMIN-only enforcement and whitespace-only normalization to none), and multi-station order routing (an order with items across several stations reporting each item's correct station via `getActiveOrders`, plus confirming CHEF's pre-existing access to view/advance active orders is untouched).
- Full accounting & tax (Phase 7): a chart-of-accounts layer (`TransactionCategory`, six protected system categories plus custom ADMIN/ACCOUNTANT-managed ones) on top of the existing `Transaction` log, deliberately kept single-entry rather than full double-entry bookkeeping. Every automatic posting (POS order, online order after payment, purchase-order receipt, payroll run) is now categorized and linked back to its source event via `referenceType`/`referenceId`, and order income transactions carry the exact tax computed at checkout via a new persisted `Order.taxAmount` (never recomputed later). Manual income/expense entries support a tax-inclusive-amount convention (tax is backed out automatically from a category's tax rate unless entered explicitly). Transactions can be recategorized and tax-corrected after the fact, but automatic (system-linked) transactions can never be deleted — only ADMIN can delete purely manual ones. Financial reporting (`getFinancialSummary`, `getProfitAndLossReport`) computes income/expense by category, net profit, and output/input VAT over a branch/date-range filter, with an Excel (.xlsx) export and a browser print view standing in for a server-generated PDF (no PDF library exists in this project). Access stays exactly ADMIN + ACCOUNTANT as before; no true customer accounts-receivable exists, since every order in this system is paid before fulfillment.
- `tests/accounting.test.ts` covering access control, category CRUD and protection of system categories, manual entry tax math (default category fallback, tax auto-extraction, explicit-tax precedence), recategorization/deletion rules, automatic linkage from POS orders/purchase-order receipts/payroll runs, the financial summary/P&L/VAT identities, and Excel export.
- Multi-branch support: a new `Branch` model (with a protected default branch) and `User.branchId` so every staff member belongs to exactly one branch, while ADMIN accounts remain branch-exempt and see/manage every branch. Inventory stock is split into a chain-wide catalog (`InventoryItem`) plus per-branch stock levels (`BranchInventoryStock`), and tables/reservations, suppliers/purchase orders, shifts, and accounting transactions are all branch-scoped end-to-end (filtering on read, targeting on create, and ownership re-checked on every update). Online orders intentionally remain branch-less for now, with ingredient stock deducted from the default branch. A new ADMIN-only Branches page (`/dashboard/branches`) and a branch selector on staff creation round out the UI.
- `tests/branches.test.ts` covering branch CRUD (including the protected-default-branch rule), cross-branch data isolation across inventory/tables/reservations/suppliers/purchase-orders/shifts/accounting, ADMIN's cross-branch visibility, moving a staff member between branches, and the online-order default-branch stock-deduction fallback.
- CRM & marketing (Phase 6): richer customer profiles (email, tags, marketing opt-in, date of birth, and ADMIN notes) alongside the existing loyalty data; ADMIN-only customer segmentation (all customers, by loyalty tier, by tag, inactive, or a computed "upcoming birthday" set) and manual SMS campaigns sent against a segment, always honoring each customer's marketing opt-in; a referral program giving every customer a shareable referral code (from signup and from their profile) with an automatic loyalty-point bonus to the referrer on the referred customer's first completed order (guarded against double payout); and post-delivery order feedback (1-5 star rating plus an optional comment, one per order) with an ADMIN feedback dashboard showing the average rating. `getCustomers`/`createCustomer` deliberately remain open to CASHIER as before (unrelated to this phase — POS checkout depends on attaching a customer to a sale); all new CRM management, segmentation, and campaign-sending surfaces are ADMIN-only. There is no background job scheduler in this deployment, so "win-back" and birthday messages are ADMIN-triggered sends against a system-computed segment rather than true scheduled automation; only the welcome message is sent automatically, synchronously, at customer signup. Customer/CRM data remains global and unscoped by branch, consistent with Phase 5.
- `tests/crm.test.ts` covering CASHIER's continued (POS-only) customer access alongside ADMIN-only CRM management, profile editing and notes, opt-in-aware segment preview, the campaign draft→send→detail lifecycle, order feedback rules (completed-only, owner-only, once-only) with the ADMIN feedback list, the referral signup/first-order-bonus/no-double-bonus flow, and birthday-segment detection.
- Staff & shift management: shift definition and staff assignment, self-service clock-in/clock-out attendance tracking, leave and shift-swap requests with a manager approval workflow (approving a leave request frees any not-yet-worked shift assignments in that date range; approving a shift-swap transfers the assignment to the target colleague), and payroll on a fixed per-user hourly rate — computed from unpaid attendance hours, booked as an accounting EXPENSE transaction at the moment payroll is run (never speculatively), with each attendance record linked to the payment that covered it so it can never be paid twice.
- `tests/staffSchedule.test.ts` covering the shift/attendance/request/payroll flow end-to-end.
- Purchasing & supplier management: full purchase-order cycle (draft → ordered → partially/fully received, plus cancellation), supplier accounts payable with a per-supplier ledger and payment recording, low-stock reorder suggestions, and cross-supplier purchase-price history. Stock, cost, and the accounting/EXPENSE booking only ever move at actual goods receipt, never at order/draft time.
- `tests/procurement.test.ts` covering the purchasing flow end-to-end.
- Online ordering & delivery: customer accounts with SMS OTP login, public menu/cart, checkout with server-verified pricing, ZarinPal payment integration (sandbox by default), order tracking, and a staff delivery dashboard with full courier lifecycle management (assign → picked up → on the way → delivered).
- Customer loyalty club: points earned per purchase and redeemable for a discount, with an automatic lifetime-spend tier (NORMAL/BRONZE/SILVER/GOLD/VIP) shared between the POS and online ordering flows.
- `tests/onlineOrdering.test.ts` and `tests/loyalty.test.ts` covering the new flows end-to-end.
- Production-build dev fallback (`npm run dev:winfix`) documented for the Node 24/Windows `next dev` Tailwind bug.
