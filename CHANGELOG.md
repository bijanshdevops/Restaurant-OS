## [Unreleased]

### Fixed
- Codebase review (Phase 19): `createRefund`'s automatic `EXPENSE` transaction — which reverses a refunded order's income — never set an `accountId`, even though Phase 18 always links the original order's `INCOME` transaction to a specific cash-flow account (cash till/bank/gateway). This silently broke Phase 18's cash-flow/reconciliation accuracy for any refunded order (e.g. a cash refund never reduced the cash-till balance). Unlike purchase-order/payroll transactions — deliberately left unclassified by Phase 18's disclosed scope, since they never had a payment-method concept — an order's payment account is always known, so this was a genuine oversight, not a scope decision. Fixed by looking up the original order's `INCOME` transaction's `accountId` inside the same `$transaction` and reusing it on the refund's `EXPENSE` transaction. Found via a self-directed review of every money-handling action file (`order.ts`, `accounting.ts`, `refund.ts`, `deliveryProvider.ts`, `reservation.ts`, `giftCard.ts`, the payroll section of `staffSchedule.ts`), per the user's confirmed Phase 19 scope ("خودم کدبیس رو مرور کنم" — self-directed review, not a user-reported issue); no other undisclosed defects were found in the files reviewed.
- `tests/refund.test.ts` gained a new regression test asserting a refunded order's `EXPENSE` transaction always carries the same `accountId` as its original order's `INCOME` transaction (12 tests total, up from 11).

### Added
- Cash flow & bank/cash reconciliation (Phase 18): a new `FinancialAccount` concept (cash till / bank / payment gateway) sits on top of Phase 7's existing single-entry `Transaction` ledger, letting a transaction be attributed to *which* account the money actually moved through. Per the user's confirmed scope, this phase deliberately targets the one real gap codebase research surfaced (no cash-till/bank-account concept, no way to catch a books-vs-reality mismatch) rather than rebuilding anything Phase 7's accounting module or the separate Modian e-invoicing module already cover. Three protected accounts («صندوق نقد» cash, «بانک» bank, «درگاه پرداخت آنلاین» gateway) are seeded with fixed IDs in the migration, mirroring how Phase 7 seeded its system categories; `ADMIN`/`ACCOUNTANT` can also create custom accounts. `createOrder` (POS) gained a new, backward-compatible `paymentMethod` ('CASH'/'CARD') parameter, surfaced as a new نقد/کارت toggle on the POS checkout screen, that links the order's automatic income transaction to the correct system account (POS previously never recorded how a sale was paid); `finalizeOnlineOrderAfterPayment` (online/QR) always links to the gateway account, since those orders only ever settle through ZarinPal. A new `AccountTransfer` model — my own architectural addition, not one of the three scoping questions asked, added because a cash-flow feature needs some way to move money between the accounts it tracks — records moves between accounts and is deliberately kept structurally separate from `Transaction` so it can never be mistaken for income/expense or distort Phase 7's P&L/VAT figures. A new `AccountReconciliation` model records a staff-counted balance against the ledger-computed balance and stores the variance; per the user's confirmed scope, no adjusting transaction is ever auto-created to zero out a mismatch — reconciliation only records and displays it. A new page, `/dashboard/accounting/cash-flow`, hosts account balances/transfers/reconciliation, kept separate from the existing accounting page. Deliberately out of scope: automatic account-linking covers only POS and online/QR (purchase-order receipts and payroll runs keep posting unclassified by default, assignable later via the extended `updateTransactionCategory`); accounts are global, not per-branch.
- `tests/cashFlowAccounts.test.ts` covering system-account seeding, POS cash/card auto-linking (via before/after account-balance deltas), online/QR gateway auto-linking, custom account creation and transfers, transfer validation, reconciliation correctly recording a variance with no automatic adjusting transaction, manual account (re)assignment via the extended `updateTransactionCategory`, and `CHEF` access-denial across every new action.
- Third-party delivery/courier integration (Phase 17): `ONLINE_DELIVERY` orders are now automatically dispatched to a third-party courier provider immediately after payment finalization, added **alongside** the existing manual/internal courier workflow rather than replacing it — per the user's confirmed scope. Since no real courier-aggregator account or API documentation exists, this ships a generic `DeliveryProviderAdapter` abstraction (`src/lib/deliveryProviders.ts`) with a single simulated adapter, `MOCK_EXPRESS` (a new `DeliveryProvider` enum), that always accepts a dispatch synchronously and returns a realistic tracking id/url — the same "always succeeds, no real merchant needed" shape as `src/lib/zarinpal.ts`'s sandbox default. `finalizeOnlineOrderAfterPayment` calls the new `dispatchOrderToThirdPartyProvider` right after its transaction commits (deliberately outside it, since dispatch is an external call); on success, `Order` gains `deliveryProvider`/`externalDeliveryId`/`externalTrackingUrl` and `deliveryStatus` becomes `ASSIGNED` directly; on failure (or no provider configured), the order is left exactly as before and simply falls back to the pre-existing manual delivery board, unchanged. Status updates after dispatch mirror the ZarinPal payment-callback pattern: `receiveDeliveryProviderStatusUpdate` is the handler a real provider's webhook would call, `src/app/api/delivery-provider/webhook/route.ts` is the real HTTP entrypoint (an optional shared-secret header guards it), and — since no real provider exists to send that webhook — two new staff-facing "simulate" actions (`simulateNextProviderStatus`, `simulateProviderDeliveryFailure`) drive the same handler from the delivery board UI, which now shows a tracking id and simulate-status controls for dispatched orders while leaving the original courier-assignment controls untouched for orders still on the internal workflow. A dedicated test-only marker string (`[TEST_DISPATCH_FAIL]` in the delivery address) makes the simulated provider deterministically reject a dispatch, letting the test suite exercise the internal-fallback path without being able to reconfigure the already-running test server's environment mid-run. Deliberately out of scope: no per-restaurant/per-order toggle to disable automatic third-party dispatch; no real provider integration beyond the one simulated adapter; no manual "retry dispatch" action for an order that fell back to the internal board.
- `tests/thirdPartyDelivery.test.ts` covering automatic dispatch on payment finalization, the delivery board surfacing a dispatched order alongside internally-managed ones, dispatch idempotency, the dispatch-failure fallback to the internal workflow (via the test marker), webhook status-update validation (unknown tracking id, unknown status), the full staff-simulated status cycle through to `DELIVERED`/order `COMPLETED`, simulated delivery failure, ADMIN/CASHIER-only access control on the simulate actions, and a regression proving `QR_DINE_IN` orders are never dispatched to a third party. Because this phase changes the default post-payment `deliveryStatus` for `ONLINE_DELIVERY` orders, `tests/onlineOrdering.test.ts` and `tests/qrDineInOrder.test.ts` were updated to match (finalize now asserts `ASSIGNED`/`MOCK_EXPRESS`, and the internal-courier full-cycle test now runs against an order carrying the dispatch-failure test marker).
- QR-code table self-ordering (Phase 16): customers scan a QR code at their table and place their own order, with **login via OTP required** (no guest ordering) and **payment online at order-creation time** through the same Zarinpal gateway as online delivery — both per the user's confirmed scope. A new `OrderChannel` value, `QR_DINE_IN`, keeps self-ordered QR orders distinguishable from POS-entered dine-in orders in analytics; `createDineInQrOrder` (`src/app/actions/order.ts`) is the first real consumer of the pre-existing but previously-unused `Order.tableId`/`Table.orders` relation. The flow reuses existing online-ordering infrastructure unmodified: `requireCustomer()`, `verifyCartItems`, `createOrderItemsWithSnapshots` (Phase 13), `applyCouponWithinTx`/`applyGiftCardWithinTx` (Phase 14), and the channel-agnostic `initiatePayment`/Zarinpal callback route. Unlike an `ONLINE_DELIVERY` order (still branch-less until fulfillment), a QR order carries a real `branchId`/`tableId` from creation (the scanned table's own branch); `finalizeOnlineOrderAfterPayment` was made channel-aware so ingredient-stock deduction and the booked income `Transaction` are attributed to the table's actual branch for `QR_DINE_IN` orders, with the previous default-branch behavior for `ONLINE_DELIVERY` orders completely unchanged, and `deliveryStatus` is only ever set for `ONLINE_DELIVERY` (a QR order goes straight to the kitchen). New customer-facing pages, `/order/table/[tableId]` and `/order/table/[tableId]/checkout` (no delivery-address field, no packaging/delivery-fee line items), mirror the existing online menu/checkout pages; the shared `OrderGate` (`src/app/order/layout.tsx`) now remembers a scanned table id across the OTP login redirect so `CustomerAuthContext.login()` returns the customer to their table's own menu, not the generic one. Each table's QR code is generated client-side on the admin Reservations page (new `qrcode` dependency) and simply encodes the table's existing UUID in a URL — no new schema field or server-issued token. Deliberately out of scope: `Table.status` is not auto-managed by QR orders (no auto-`OCCUPIED` on order, no auto-revert on completion); the QR code has no separate rotating/expiring token beyond the table's own UUID; the cart is shared between the online-delivery and QR dine-in flows (same `CartContext`); and no packaging cost is charged on QR dine-in orders (food is served on plates, not packaged).
- `tests/qrDineInOrder.test.ts` covering `getTableForOrder` for valid/invalid tables (unauthenticated, as needed before OTP login), `createDineInQrOrder` requiring OTP login and rejecting an invalid table or an empty cart, correct total (no packaging/delivery fee)/channel/`tableId`/`branchId`/zero-`deliveryFee` on a successful order, `finalizeOnlineOrderAfterPayment`'s branch-aware stock deduction and income-transaction attribution to the table's own branch with `deliveryStatus` left unset, a regression test proving the existing `ONLINE_DELIVERY` finalize path (default-branch stock deduction, `deliveryStatus` set) is completely unaffected, and `getMyOnlineOrder` correctly reused for tracking a QR order with proper customer-ownership isolation.
- Combo meals & Happy Hour scheduled pricing (Phase 15): both sub-features shipped together, management scoped to **ADMIN-only** (matching Phases 13/14). A `Combo` (fixed-price bundle) is represented internally by a dedicated, hidden shadow `MenuItem` (`isCombo: true`) whose title/price/kitchen-station/availability `src/app/actions/combo.ts` keeps in sync — this means the cart, POS grid, online menu, kitchen board, printer/receipts, refund flow, and sales analytics need **zero code changes** to support combos; only `src/lib/recipeExpansion.ts` had to become combo-aware, expanding ingredient usage from `ComboItem` components (each component's own recipe × its quantity in the combo) instead of `RecipeItem` rows. A combo cannot contain another combo (rejected server-side) and does not support modifiers in this phase; a new `OrderItemComboComponent` table snapshots each combo's components at order-creation time. Deleting a never-ordered combo removes both the `Combo` row and its shadow menu item outright; deleting one already used in an order deactivates both instead (`deactivatedInstead: true`), mirroring Phase 14's coupon-deletion pattern. Separately, a new `HappyHourRule` (`PERCENT` 1-100 or `FIXED`) targets one or more non-combo menu items via `HappyHourRuleItem`, active on a set of `daysOfWeek` (JS `Date.getDay()` convention) within a `startMinute`-`endMinute` window with correct midnight-crossing handling; the pure calculation logic (`isRuleActiveNow`, `ruleDiscountAmount`, `computeEffectivePrice`) lives in a new, database-free `src/lib/happyHour.ts` shared by order pricing and reusable by future menu-display code. When multiple active rules match the same item, the one giving the largest discount wins. `verifyCartItems` in `order.ts` computes the Happy-Hour-adjusted price at order-creation time and snapshots it per line on `OrderItem` (`happyHourRuleId`, `happyHourRuleName`, `happyHourDiscountPerUnit`), immune to later rule edits/deletion (`onDelete: SetNull`, independent name snapshot) — the same snapshot pattern Phases 13/14 established. Deliberately out of scope: Happy Hour never applies to combos (enforced server-side, not just hidden from the picker); the admin UI does not detect/block overlapping Happy Hour rules at save time; "now" for Happy Hour matching is the server's own clock, with no explicit restaurant-timezone concept; the `OrderItemComboComponent` snapshot is captured but not yet shown on the kitchen ticket or printed receipt; and the POS/online browsing screens do not show a live Happy-Hour-discounted price (only the real order-creation charge is discounted, which is what the tests verify).
- `tests/combosHappyHour.test.ts` covering ADMIN-only access control on all 10 new actions, combo creation/validation including the combo-in-combo rejection, combo ordering proving the bundle price (not the sum of components' prices) is charged and each component's own recipe is deducted from inventory in the correctly multiplied amount, the `OrderItemComboComponent` snapshot's contents and a unique kitchen station for the whole combo line, combo deletion's hard-delete-vs-deactivate behavior, a combo-order refund proving ingredient restocking still works unchanged through the existing refund flow, Happy Hour rule validation (percent range, fixed positivity, day/time-range/item requirements, combo-target rejection), unit tests of the pure `src/lib/happyHour.ts` functions (ordinary and midnight-crossing time windows, day-of-week/`isActive` gating, discount-amount clamping, and the largest-discount-wins tie-break), and integration tests through real order creation using the actual server clock proving the discount is/isn't applied correctly on the right day/time and is never applied to a combo.
- Gift cards & discount coupons (Phase 14): both sub-features shipped together, management scoped to **ADMIN-only** (matching Phase 13's access model). New `GiftCard`/`GiftCardTransaction` models (unique code, `initialBalance`, a `currentBalance` that only ever decreases, optional expiry/note/customer link, and a full `ISSUE`/`REDEEM` transaction ledger per card) and a new `Coupon` model (unique code, `PERCENT`/`FIXED` discount, optional `minOrderAmount` and `maxUses` with a tracked `usesCount`, optional expiry, `isActive` toggle). Both `createOrder` (POS) and `createOnlineOrder` (online) accept an optional coupon code and/or gift card code and apply them inside the same `$transaction` that creates the order — an invalid/expired/exhausted/deactivated code throws and rolls back the entire order rather than being silently ignored. The calculation layering is: gross subtotal → tax on the gross subtotal (unchanged) → coupon discount → loyalty-points discount (online only, computed post-coupon) → gift card applied last, capped at the remaining amount due. The order snapshots exactly what happened (`couponCode`, `discountAmount`, `giftCardAmountUsed`, a `GiftCardTransaction` of type `REDEEM`), so later edits to the coupon/gift card never retroactively change a past order — the same snapshot pattern Phase 13 established for recipe usage. Two new non-transactional, unauthenticated preview actions (`checkGiftCardBalance`, `checkCouponForOrder`) let the online checkout page show a live balance/discount preview before the customer submits the order, without mutating any state. A deleted coupon that has never been used is removed outright; one that has already been used on an order is deactivated instead (so historical orders keep a resolvable `couponCode`). Deliberately out of scope: no accounting transaction is booked when a gift card is issued (only redemption on an order produces income, unchanged); refunding an order (`refund.ts`) does not restore gift-card balance or decrement a coupon's `usesCount`; the admin gift-card issuance UI has no customer-picker (generic issuance only).
- `tests/giftCardsCoupons.test.ts` covering ADMIN-only access control on all management actions (and confirming the two preview actions need no auth), gift-card issuance and balance/duplicate-code/invalid-amount validation, coupon-creation validation (percent range, fixed positivity, duplicate code), coupon application on an order (percent-discount math and `usesCount` increment, fixed-discount clamping to subtotal, `minOrderAmount`/`maxUses`/expiry/deactivation rejection, invalid-code full-order-failure), gift-card redemption on an order (partial-drain and full-drain-to-zero math, zero-balance/deactivated-card rejection, invalid-code full-order-failure), the combined coupon+gift-card layering formula with exact numeric assertions, the refund-non-reversal test (a full refund leaves gift-card balance and coupon `usesCount` unchanged), and coupon deletion's hard-delete-vs-deactivate-when-used behavior.
- Precise Recipe/BOM (Phase 13): three sub-features shipped together, all ADMIN-only (matching the existing recipe/BOM access model) — (1) **Yield % (waste)**: `RecipeItem`/`SubRecipeItem` gained a `yieldPercent` field (default 100); the effective inventory deduction for a line is `quantity / (yieldPercent / 100)`, so a 50% yield on a 2-unit line deducts 4 units. (2) **Sub-recipes**: a new `SubRecipe`/`SubRecipeItem` model pair supports arbitrarily nested sub-recipe-of-sub-recipe formulas, with cycle detection (`assertNoSubRecipeCycle`, BFS-based) and a depth cap (`MAX_SUBRECIPE_DEPTH = 12`) enforced during expansion; a sub-recipe in use by a menu item or another sub-recipe cannot be deleted. (3) **Modifiers/add-ons**: new `ModifierGroup`/`Modifier`/`MenuItemModifierGroup`/`ModifierRecipeItem` models let a menu item offer optional add-ons with a `priceDelta` and a signed inventory effect (a modifier's recipe-line quantity can be negative, e.g. "no cheese"; the deduction is clamped at zero, never negative); each `ModifierGroup` enforces `minSelect`/`maxSelect` server-side at order time. All formula expansion (base recipe + sub-recipes + selected modifiers) runs through one shared library, `src/lib/recipeExpansion.ts`, used by both real order-time stock deduction and the cost-analysis (Phase-just-prior) screen, so there is never a second, divergent implementation of "what does this item's formula mean" — cost analysis deliberately still excludes modifier effects in this pass. As part of this phase, a pre-existing latent bug was found and fixed: refund restocking previously recomputed quantities from the *live* recipe, so editing a recipe between an order and its later refund would silently restock the wrong amount. Fixed by snapshotting the fully-expanded per-unit ingredient usage (`OrderItemIngredientUsage`) and the selected modifiers (`OrderItemModifier`) once, at order-creation time, and having both the stock-deduction step (immediate for POS, deferred to payment-finalization for online orders — timing unchanged from before this phase) and the refund restock step (`refund.ts`) read that snapshot instead of the recipe as it exists today. Separately, an unplanned reliability bug in `recipeExpansion.ts` itself was found and fixed during this phase's own test development: calling the shared client from inside a `prisma.$transaction` callback (instead of the transaction's own client) could intermittently starve the connection pool, causing rare non-deterministic order/sub-recipe-save failures with no surfaced error; fixed by threading an explicit database-client parameter through every function in the library and having every transactional caller (`order.ts`, `subRecipe.ts`) pass its own transaction client.
- `tests/preciseRecipe.test.ts` covering ADMIN-only access control on all 8 new actions, yield-% deduction math, sub-recipe expansion and cost roll-up, direct and indirect sub-recipe cycle rejection, delete-while-in-use rejection, modifier price/inventory effects (including the zero-floor clamp on a negative modifier), `minSelect`/`maxSelect` enforcement, a modifier rejected when it belongs to a different menu item, and — the key correctness test — that refunding an order restocks the *original, snapshotted* ingredient amount even after the underlying recipe was changed multiple times between order creation and refund, for both the POS and online-order (payment-finalization) paths.
- Waitlist & reservation deposits (Phase 12): a new `WaitlistEntry` table (`WAITING`/`SEATED`/`CANCELLED`) for walk-in guests with no future time or pre-assigned table — deliberately kept separate from `Reservation` for that reason — with `getWaitlist`, `joinWaitlist`, `seatFromWaitlist`, `cancelWaitlistEntry` (`ADMIN` + `CASHIER`, matching the existing reservation access model). `seatFromWaitlist` mirrors `updateReservationStatus`'s `SEATED`-branch table-sync logic (table becomes `OCCUPIED`) inside a `$transaction`. Separately, `Reservation` gained `depositAmount`/`depositRefundedAt`: an optional staff-collected deposit at `createReservation` time books a real `INCOME` transaction (new system category `INCOME_RESERVATION_DEPOSIT`, `referenceType: 'RESERVATION_DEPOSIT'`) in the same `$transaction` as the reservation. Refunding a deposit is a new, separate, explicit action (`refundReservationDeposit`) — never triggered automatically by any reservation-status change — that books a full, unconditional refund (an `EXPENSE` transaction, `EXPENSE_RESERVATION_DEPOSIT_REFUND` category) at any time, including after cancellation or no-show, per the confirmed "full refund at any time" policy; the original `INCOME` transaction is never touched, consistent with the Phase 7/10 reference-backed-transaction rule. Deposit/refund events are not added to the Phase 11 audit log (out of that phase's locked-in scope). Reservations UI (`/dashboard/reservations`) gained an optional deposit-amount field on reservation creation, a refund action per reservation, and a new waitlist panel (join/seat/cancel).
- `tests/waitlistDeposits.test.ts` covering access control (`CASHIER` allowed, `CHEF` denied, on every new action), deposit collection producing a correctly-shaped `INCOME` transaction (and no transaction at all when no deposit is given), deposit refund producing a correctly-shaped `EXPENSE` transaction while leaving the original `INCOME` transaction untouched, blocking a second refund and blocking a refund with no deposit, refunding successfully regardless of reservation status (including after `CANCELLED`), the waitlist join→seat flow's table-status sync, seating-twice rejection, waitlist cancel, and branch isolation for both the waitlist and deposit-refund actions.
- Audit log (Phase 11): a new `ADMIN`-only activity log (`getAuditLogs`, `getAuditActionList`, `/dashboard/audit-log`) recording sensitive events only — user login (success and failure), user creation/deletion, financial-transaction deletion/recategorization, refund creation, restaurant/Modian settings updates, and payroll runs. Backed by a new `AuditLog` table (`actorUserId` nullable with `onDelete: SetNull` so deleting a user never blocks on its own audit history, `actorName`/`actorRole`, `action` enum, `entityType`/`entityId`, `metadata` JSON, `success`, `createdAt`) and a single non-throwing `logAudit()` helper (`src/lib/auditLog.ts`) that accepts the current `prisma.$transaction` client so log rows for `runPayroll`/`createRefund` commit or roll back atomically with the operation they describe. Role changes are explicitly *not* logged, because no role-update action exists anywhere in this codebase (roles are only ever set once, at user creation) — confirmed by re-reading `user.ts` before finalizing this phase's event list. Every normal read, and every ordinary POS/online order, is deliberately never logged, per the "sensitive events only" scope decision.
- `tests/auditLog.test.ts` covering ADMIN-only access to the log viewer, a correctly-shaped log row for every instrumented event (login success/failure including the no-actor/no-password case, user create/delete, transaction delete/update, refund creation, both settings-update paths with the Modian API key never appearing in logged metadata, and payroll runs), and that an ordinary POS order produces no audit row at all.
- Refunds & returns (Phase 10): a new ADMIN-only module (`getRefunds`, `findOrderForRefund`, `createRefund`, `/dashboard/refunds`) for reversing a `COMPLETED` order, either partially (specific item/quantity lines) or fully (the entire remaining, unrefunded balance). Refund state is tracked entirely through two new tables (`Refund`, `RefundItem`) and a new `OrderItem.refundedQuantity` counter — deliberately not a new `Order` status, so `Order.status` stays `COMPLETED` forever and nothing in the existing kitchen/active-orders status filtering had to change; only `COMPLETED` orders are eligible (an order still mid-kitchen must be advanced or cancelled first, out of scope for this phase). Each refund event books a brand-new `EXPENSE` transaction (system category "مرجوعی و استرداد") rather than touching the order's original `INCOME` transaction, consistent with the Phase 7 rule that a reference-backed transaction can never be deleted or reduced — `getFinancialSummary`/`getProfitAndLossReport`/VAT netting all pick this up automatically with no code changes. Refunded item quantities always restock `BranchInventoryStock` via the menu item's recipe (BOM), on the assumption the returned goods are sellable — there is no damaged/spoiled-goods distinction. Tax is reversed proportionally to the refunded items' share of the order's original subtotal; packaging cost is only refunded on a full refund (using the *current* restaurant-settings packaging cost, since `Order` never persisted the packaging cost actually charged at checkout time) and never prorated for a partial refund; delivery fee is never refunded in any case. When the order has a customer, loyalty points and lifetime stats are reversed proportionally to the same ratio (points clawed back for points earned, points returned for points redeemed on that order, `totalSpent` decremented and floored at zero, tier recomputed), and `totalOrders` is decremented only when the refund is explicitly a full refund. As part of this phase, a pre-existing gap was fixed in `createOrder`: `Order.pointsEarned` was never persisted for POS orders (only the online-order flow set it), which would have silently zeroed out the new proportional points-clawback for the majority of orders — it is now stored at order-creation time using the same calculation `awardLoyaltyForOrder` already performed. Sales analytics (Phase 9) is *not* updated to reflect refunds in this phase — refunded revenue continues to appear at its original, unadjusted value there.
- `tests/refund.test.ts` covering ADMIN-only access control, `COMPLETED`-only eligibility, full-refund total/eligibility-exhaustion (including that a fully refunded order can't be refunded again), the automatic EXPENSE transaction and its non-interference with the original INCOME transaction, proportional tax math on partial refunds, over-refund and invalid-line-item rejection, inventory restock correctness across a partial-then-full refund sequence, and proportional loyalty/customer-stat reversal (including the `totalOrders` full-refund-only decrement and the `Order.pointsEarned` persistence fix).
- Sales analytics / BI dashboard (Phase 9): a new read-only reporting module (`getSalesAnalytics`, `/dashboard/analytics`) built purely from existing order data — no new data-entry surfaces. "Real sales" are defined as any order whose status is not `CANCELLED`/`AWAITING_PAYMENT` (matching exactly when the accounting module books income), a fixed rule that is not user-configurable; date range and branch remain the only filters, defaulting to the last 30 days when no range is given. Reports include KPI cards (total revenue/orders/average order value), a daily revenue trend, top-10/bottom-10 menu items by revenue/quantity (limited to items with at least one sale in the period), a per-branch comparison, a 24-hour peak-hours breakdown, and a sales-channel (dine-in/takeaway/online) mix. Access is ADMIN + ACCOUNTANT, reusing the Phase 5/7 branch-scoping pattern (ACCOUNTANT locked to their own branch; branch-less online orders remain visible under any branch filter, as in accounting). No export feature and no forecasting/cohort analytics in this pass.
- `tests/analytics.test.ts` covering access control (ADMIN/ACCOUNTANT allowed, CASHIER/CHEF denied), the default 30-day window, the CANCELLED-exclusion rule for "real sales," explicit date-range filtering, per-item/per-branch/per-hour/per-channel aggregation correctness, and ACCOUNTANT branch-scoping (including that a non-admin's own-branch view still surfaces branch-less online orders, and that a non-admin cannot override their branch via a client-supplied `branchId`).
- Kitchen display multi-station routing (Phase 8): a new optional `MenuItem.kitchenStation` free-text tag (set by ADMIN in menu management), and station tabs on the existing kitchen board (`/dashboard/kitchen`) computed live from what's currently active in the queue — selecting a station filters tickets to the ones containing that station's items and shows only those items within each ticket. The pre-existing single-queue PENDING/PREPARING/READY board, its elapsed-time-since-order warning, and its ADMIN+CHEF page access (with `getActiveOrders`/`updateOrderStatus` staying CASHIER-accessible as before) are all unchanged. Order status remains per-order rather than per-item, so a ticket's status buttons still advance the whole order even from a single-station view; there is no configurable prep-time target/SLA, only the existing simple elapsed-time warning.
- `tests/kitchen.test.ts` covering kitchen-station CRUD on menu items (including ADMIN-only enforcement and whitespace-only normalization to none), and multi-station order routing (an order with items across several stations reporting each item's correct station via `getActiveOrders`, plus confirming CHEF's pre-existing access to view/advance active orders is untouched).
- Full accounting & tax (Phase 7): a chart-of-accounts layer (`TransactionCategory`, six protected system categories plus custom ADMIN/ACCOUNTANT-managed ones) on top of the existing `Transaction` log, deliberately kept single-entry rather than full double-entry bookkeeping. Every automatic posting (POS order, online order after payment, purchase-order receipt, payroll run) is now categorized and linked back to its source event via `referenceType`/`referenceId`, and order income transactions carry the exact tax computed at checkout via a new persisted `Order.taxAmount` (never recomputed later). Manual income/expense entries support a tax-inclusive-amount convention (tax is backed out automatically from a category's tax rate unless entered explicitly). Transactions can be recategorized and tax-corrected after the fact, but automatic (system-linked) transactions can never be deleted — only ADMIN can delete purely manual ones. Financial reporting (`getFinancialSummary`, `getProfitAndLossReport`) computes income/expense by category, net profit, and output/input VAT over a branch/date-range filter, with an Excel (.xlsx) export and a browser print view standing in for a server-generated PDF (no PDF library exists in this project). Access stays exactly ADMIN + ACCOUNTANT as before; no true customer accounts-receivable exists, since every order in this system is paid before fulfillment.

- Multi-branch support: a new `Branch` model (with a protected default branch) and `User.branchId` so every staff member belongs to exactly one branch, while ADMIN accounts remain branch-exempt and see/manage every branch.
