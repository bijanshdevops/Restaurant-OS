# Operations & Runbooks

Welcome to the Operations manual for Restaurant-OS. This document outlines how to maintain the health of the system, debug asynchronous workflows, and resolve production bottlenecks.

## 1. Tracing a Request (Correlation IDs)

Every single API request generated by a client or the frontend Dashboard is automatically assigned a UUID via `AsyncLocalStorage`.

**How to use it:**
If a customer reports that Order `ord_123` failed to show up in their Accounting software:
1. Query the primary application logs for `ord_123`.
2. Extract the `correlationId` from that log line (e.g., `req_abc_789`).
3. Search your central logging provider (Datadog, CloudWatch, Kibana) for `"req_abc_789"`.
4. You will see the exact chronological flow: the API Controller accepting the payload, the Domain Event being published, and the Webhook attempting to fire.

## 2. Managing the Transactional Outbox

The Outbox pattern guarantees event delivery to external Webhooks, but Webhooks can fail due to network timeouts.

**Understanding Outbox States:**
- `PENDING`: Waiting to be picked up by the OutboxProcessor.
- `PROCESSING`: Locked by a worker to prevent duplicate delivery.
- `PROCESSED`: Successfully transmitted.
- `FAILED`: Exhausted all exponential backoff retries.

**Runbook: Retrying a FAILED Webhook**
If a third-party API goes down for 24 hours, events will eventually transition to `FAILED`. To manually retry them:
```sql
UPDATE "OutboxEvent"
SET status = 'PENDING', attempts = 0, "nextRetryAt" = NOW()
WHERE status = 'FAILED' AND "eventType" = 'OrderPaidEvent';
```
The background processor will instantly pick them up on its next polling cycle.

## 3. Resolving Inventory Deadlocks

We utilize Optimistic Concurrency Control (OCC). There are no physical database deadlocks. Instead, concurrent users trying to buy the exact same item will experience a rejection (400 Bad Request: `InsufficientStockException`).

**Monitoring Concurrency:**
If you notice an unusually high volume of `400` responses in the logs with the OCC signature, it indicates a "flash sale" scenario. 
- Ensure that the frontend is caching inventory numbers efficiently.
- In extreme cases, you may configure the API Gateway `ThrottlingMiddleware` to aggressively rate-limit the `/api/orders` route to smooth out the traffic spikes.

## 4. API Gateway & Throttling
We limit requests to 100 per minute per `tenantId`.
If a tenant legitimately needs higher throughput:
1. You can modify the `RateLimiter.ts` configurations to accept environmental overrides.
2. In a multi-node production setup, ensure that `RateLimiter.ts` has been refactored to use a centralized Redis store rather than the local V8 memory map.
